# spec｜宝可梦 VC 初代日版实时 OCR 翻译

**本文件只定义产品需求、验证方法和验收标准。** 执行方式见 `AGENTS.md` 和 `.agent/PLANS.md`；实施步骤与当前结果见 `.agent/EXECPLAN.md`。从零开发，不继承历史实现或测试结论。

## 1. 目标、技术边界和范围

开发 **Windows 10 x64 / Java 8 / JavaFX 8 / Maven** 本地工具：从投屏窗口识别 **3DS VC 日版《宝可梦 红、绿、蓝、皮卡丘》**的当前可见日文，在**独立窗口**按画面类型显示中文。无需用户选择游戏版本；来源版本仅辅助歧义消解。

- **运行时输入**：真实投屏窗口；不读 3DS 内存，不改 ROM、存档、游戏或投屏进程，不覆盖游戏原画面。
- **离线动态测试输入**：**只使用用户现有的 4 段实机原始录像**；不要求补录/重录，不使用模拟器或其他视频作为替代。已有截图可作可选的静态辅助，不能替代连续帧测试。
- **技术**：实际日版像素字库 + 确定性图像算法；不引入额外 OCR、视觉或语言模型作产品组件或 GT 制作/核验依赖。开发期可用 FFmpeg/FFprobe 读取视频；正常使用不依赖 Python 和测试答案。
- **必需场景**：主文本框、探索/对话、战斗提示与技能选择、背包、宝可梦状态菜单、PC、商店。图鉴翻译不作必需项，但不得在非目标画面误输出文字。
- **画面变化**：整倍/非整倍缩放、阴影、清浊点、逐字加载、短提示、翻页、滚动、清屏、光标和菜单切换、黑帧/无效帧。场景分类未知时，明确的主文本框仍应识别。
- **窗口采集**：支持窗口前台、非前台及被其他窗口遮挡时的有效画面采集；不能把遮挡后的桌面截图冒充目标窗口。最小化/采集失败允许“无有效帧”，但必须清除过期译文。

## 2. 最小系统设计

```text
真实投屏窗口 / 现有4段录像
  → Capture（RGB、尺寸、原时间）
  → OCR（区域、像素字格、原始日文与候选）
  → VisibleState（当前文字、加载/清屏/光标/滚动）
  → Translator（日文来源、变量、候选消歧、当前页中文）
  → UI（独立窗口显示、失效清理与诊断）
```

各阶段独立测试、分别存储中间结果。**先独立验收日文 OCR，再建设生产中文映射。** “原始 OCR”不得用源码候选或中文答案纠错；可选的“日文辅助修正”须保留原始结果、字形候选及修正理由，不能因为存在译文就改字。

### 字形与可见页面

- 审计**日版**反汇编中的字库、编码、渲染/打印指令以及红绿蓝黄差异，识别假名、标点、数字、字母、空格和特殊符号。
- 先恢复画面比例、像素网格与字格，再处理阴影、背景、浊点/半浊点和上方标记。保留原帧裁剪、坐标、候选与处理参数；不要用文本索引覆盖图像错误。
- 区分**完整源码消息**与**当前可见页/字段**。换行、变量、等待、清屏、逐字显示、滚动和残留均按真实显示语义处理。当前页面完整不要求整条消息已结束；不得提前翻译未显示的后续内容。

### 中文和变量

- 四版本可共用日文索引，必须保留版本/路径/变量/来源。检索依次尝试可见日文精确匹配、安全规范化、受约束变量模板；有冲突再用场景/历史消歧，**不能直接选第一条**。
- 玩家/劲敌名、宝可梦昵称/物种、招式、道具、等级、HP/PP、经验、数量、金额等保留**角色、显示值和类型/格式**；否定、大小假名、名字及数字不能被错误归一化。
- 中文须依日文语义、来源脚本/版本和变量角色核对；国际版脚本和汉化仅是候选，不得靠行号/顺序自动对应。未知、冲突或不完整时显示原文/未翻译状态。

实施时核实提交、文件范围与许可的参考资源：日版 [pokegreen](https://github.com/Narishma-gb/pokegreen)、[pokeblue](https://github.com/Narishma-gb/pokeblue)、[pokeyellow-jp](https://github.com/Narishma-gb/pokeyellow-jp)；结构辅助 [pret/pokered](https://github.com/pret/pokered)、[pret/pokeyellow](https://github.com/pret/pokeyellow)；语料候选 [poke-corpus](https://github.com/abcboy101/poke-corpus)；中文候选 [pokeredCHS](https://github.com/TomJinW/pokeredCHS)、[pokeyellowCHS](https://github.com/TomJinW/pokeyellowCHS)。**参考仓库不等于数据已审计或有再发行许可。**

## 3. 录像验证设计（无需额外模型）

**Ground Truth（GT）**指从**真实原始画面独立核验**的日文文字、位置、显示状态及时间边界；译文有单独的中文 GT。**测试答案必须先于被测程序输出形成，且不可从该输出复制。** 允许当前编码代理直接看图完成双遍核读，不引入其他模型。两遍均独立于被测 OCR/生产翻译输出，不要求两个不同核验者；必须如实记录“代理核读/复核”，不得声称人工逐帧核验。代理负责连续完成各场景标注，**所有场景的 GT 按 §3.4 收口后一次性提交用户审阅**，不在单个片段或部分场景完成时设置人工卡点；不要求用户日常逐帧标注。代理无法可靠核读的范围保持待验证，用户批准不能替代缺失证据。

### 3.1 固定原始素材与覆盖矩阵

- 唯一离线**视频**素材池是用户**已有的 4 段实机录像**。原文件从 `testpic/video/` 只读引用，或原样置于 `data/raw/video/`；实际文件身份须在清单中核验。仅继承这四个原媒体，**不继承旧代码、账本、GT、通过结论**。
- 开始先核对 **4 个**实际源文件的 SHA-256、时长、解码情况、原始帧时间及显示内容，并给出游戏版本/真实会话的**画面或来源证据**；文件名不是版本/场景证明。原件不得覆盖、重编码或修改。
- 在**四录像已有的内容中**，按覆盖矩阵预选足量**代表性连续 clip**，覆盖实际出现的对话、战斗、背包、状态、PC、商店；逐字加载→完整、翻页/滚动、清屏/退出、光标、短提示、无效/黑帧；浊点、变量名、数字、阴影和不同缩放。每段长度按事件的前后文决定，不用固定秒数或“每场景 N 段”配额。
- **片段内 100% 连续原帧**保留/可重放，包括失败、空帧和只出现一帧的文字。未选时段标为“未验证”；不要求先把四个整视频全文标注一遍。
- 分组优先按**可证实独立游戏会话**划分 `development`（开发）、`regression`（回归）、`acceptance`（冻结验收）。不能把同一会话的相邻/重叠片段当成独立验收来源。若四段录像不具备独立验收会话，就持续进行开发和回归，而将独立验收标为“待验证”；**不要求录新视频**。

每次报告：四个源媒体身份、总时长与已选时长、评分帧数/片段数/页面机会数、版本/场景/转换覆盖、会话隔离依据，以及未选范围和缺失维度。**已选片段通过≠四视频全部通过≠游戏全范围通过。**

**独立会话**：一次具有连续游戏上下文的实际游玩过程；同一次过程的分段、裁剪、转码或重复文件不增加会话数。来源证据与画面连续关系用于确认分组，文件名、数量或日期不能单独证明独立性。验收会话还必须未用于开发调参；来源关系不明时记待验证。GT 独立于程序输出，与验收会话独立于调参材料是两个不同条件。没有可证实且未用于调参的独立会话时，只能继续允许范围内的开发/回归；M4 不通过，M5 生产中文映射不得启动，不要求补录。

#### 完整事件片段的判定

完整事件片段必须包含**事件发生前的可见状态 → 全部变化过程 → 事件结束后的可见状态**，使文字出现、变化和失效的边界可复核。事件可以是一次页面显示、菜单操作或滚动，不要求覆盖整段剧情或整场战斗；事件范围与选择理由须事前登记，不能为避开难帧任意缩小。

| 事件类型 | 起点须包含 | 终点须包含 |
| --- | --- | --- |
| 对话/页面显示 | 文本框出现或本页文字开始加载前的状态 | 本页被翻页、清屏或关闭的完整转换及之后状态 |
| 菜单操作 | 操作前的菜单、字段和光标位置 | 光标移动、进入或退出的完整转换及操作后界面 |
| 战斗提示 | 提示出现前的画面 | 加载、完整提示、替换或消失，以及下一状态 |
| 滚动文字 | 滚动前的全部可见内容 | 滚动全过程与滚动后保留/新增的可见内容 |
| 短暂提示 | 提示出现前的状态 | 全部可见帧和消失后状态；仅一帧也不能跳过 |

先浏览上下文，再以不读取 OCR 的像素/布局变化定位候选边界，最后由代理逐帧核查边界附近并向两侧扩展。像素差异只用于导航，背景动画或光标闪烁不自动代表事件开始/结束；**不能仅凭文字连续若干帧不变认定页面完整或事件结束**，必须结合实际后续画面与显示语义确认。观察到下一状态不意味着可以在其加载中途结束一个声称覆盖该下一事件的片段；片段末尾仅用于确认上一事件结束的后文，应明确标为上下文。

如片段开头已在半句话、滚动或菜单切换中，必须向前追溯真实历史；需要的历史作为 warmup 保留。clip 总范围、热身、评分范围和结束后上下文分别登记，待验证事件的全部目标转换必须位于评分范围内，不能把加载/清屏/失败帧移入非评分范围来提高成绩。相邻片段重叠的同一原始页面机会，汇总时不得重复计数。

若源录像本身从事件中间开始、在事件结束前停止，或存在无法核清的边界/解码缺口，登记 `truncated_start`、`truncated_end` 或 `boundary_unknown` 及原帧证据；保留这些候选与覆盖缺口，不作为完整事件冻结验收，也不要求补录。可另外选择同一录像中边界完整的其他事件，但须在运行被测 OCR 前说明选择依据；不能事后删除冻结范围中的失败。每个候选均记录事件类型、起止依据、边界状态及双遍核查证据，随 §3.4 材料交用户审阅。

### 3.2 基准建立与比对的 8 步

1. **建原始帧账本**：每个解码帧记录 `frameIndex、整数pts、durationPts、time_base、宽高、RGB SHA-256、解码错误`；媒体另存 SHA-256、解码器版本/参数及缺口。时间使用 `pts × time_base`；不靠猜测 FPS 或播放器百分比。直接连续解码原视频，按显示顺序登记所有帧；不得以播放器/桌面截图、定时抽样、仅关键帧、去重、插帧或固定帧率重采样代替原帧。固定像素格式、色彩转换及方向处理参数；缺失/异常时间戳、时长或解码失败必须登记，不能静默猜测、补齐或丢弃后视为通过。无损帧保存是对固定解码所得 RGB 像素的无损保存，不宣称恢复录像压缩前的画面。
2. **事前选片**：保存源媒体哈希、`[startFrame,endFrameExclusive)`、对应 PTS、真实上下文/热身和**独立评分范围**、选择理由及所属集合。只根据真实画面与覆盖要求选片，**不能看主 OCR 是否成功再选**。
3. **完整保帧**：评分段内所有帧按原顺序与时间可追溯；使用连续可见状态区间标注，每个区间映射回每一原帧。文字、字段位置、加载程度、光标、滚动或清屏变化时拆分区间；背景变化须核查是否影响目标区域，不能仅凭差异阈值判断状态不变。可先以开发集一个完整事件试标并验证格式，再连续扩展全部场景；试标是内部格式检查，不单独触发人工卡点，也不提前冻结。
4. **第一遍盲读 GT**：仅看原视频、原帧与放大字格，记录文字、字段、坐标、加载程度、完整页/空状态和起止帧，不看 OCR、生产翻译或它们的候选答案。
5. **第二遍独立核对并统一提交人工审阅**：当前代理重新从原视频取原帧及相邻原帧核查难字、浊点、名字、数字、单帧变化及边界；配合**不读取 OCR 的**像素/布局变化扫描找漏掉的转换。必要时按真实字库逐格对照；源码只解释控制路径，不替代画面证据，后帧文字不得提前填入前帧。每段完成双遍后保存候选和检查证据，继续其他场景；**只有全部场景按 §3.4 收口后**，才统一提交完整材料并停止，等待用户明确批准。
6. **冻结 GT**：仅在相应材料版本获用户批准后执行。每个评分帧必须恰有一个明确的可见状态区间覆盖，可在区间内部列多文本区域；文字、位置、时间、空状态等有原帧及双遍核对证据。`unknown/unreviewed/conflict` 不能被默认为正确，也**不能冻结该未解决评分范围**。冻结记录哈希与版本及批准依据，修改另存版本并说明依据。
7. **原时间轴回放**：测试驱动按原 PTS 提供像素、尺寸与时间，必要时从**真实历史**热身。生产 OCR/翻译只能看正常输入和配置，**不能看 GT、片段 ID、评分集合标签**。不为使结果通过而延长短页；实际结果和 GT 由独立测试驱动比对。
8. **回归与验收隔离**：保存错误类型、失败原帧/前后文及输入、构建、数据与 GT 版本。验收片段一旦用于调参，整个关联会话退出独立验收集；仅从原有四视频中剩余独立会话另建，否则验收“待验证”，**不要求补录**。

### 3.3 最少数据契约

所有测试元数据采用 UTF-8 JSON/JSONL；原媒体只读，GT、实际输出和报告分开。

| 文件（建议路径） | 内容 |
| --- | --- |
| `data/meta/media.jsonl` | 4 个媒体的路径、哈希、游戏/会话来源证据、解码配置 |
| `data/meta/frames.jsonl` | 媒体 ID、每帧编号、PTS/time_base、时长、像素哈希、宽高及错误 |
| `data/meta/clips.json` | clip ID、源 ID/源区间、热身/评分/结束后上下文区间、真实时间、事件类型、起止依据及原帧证据、边界状态、选片理由、集合及覆盖标签 |
| `data/gt/ocr.jsonl` | 区间 `[startFrame,endFrameExclusive)`、状态、可见日文/区域/坐标、证据、核验状态；评分帧无缝、无重叠覆盖 |
| `data/gt/zh.jsonl` | 按可见状态 ID 独立关联中文语义、变量与证据（不得复制生产翻译表） |
| `reports/.../actual.jsonl` / `report.json` | 程序原时序输出、逐机会差异、错误、性能、统计分母与覆盖缺口 |

稳定 ID 基于源媒体和原始边界，不能从 OCR 答案生成。冻结 GT 保留旧版本及哈希；未标注、冲突、来源不明不得从统计中偷偷删除。

### 3.4 全部场景 GT 收口后的统一人工卡点（强制）

- **提交单位**：日文 GT 在 M1–M2 按全部场景组织成**一个统一审阅版本**。试标、单个片段、单个场景或少量场景完成后，代理继续候选生成、双遍核读及必要的离线定位/标注/完整性工具工作，不拆成多次人工审批；不得在统一批准前冻结新增 GT、开发或运行被测 OCR/翻译。后续中文 GT 仍须等 M4 日文 OCR 独立验收通过后，在其阶段按全部应译场景统一收口、单独审阅；不能为“一次性”而提前建设中文 GT 或生产中文映射。
- **全部场景的含义**：以现有四录像的覆盖矩阵为边界，逐项处理主文本框、探索/对话、战斗提示、技能选择、背包、宝可梦状态菜单、PC、商店，以及实际存在的非目标/黑帧/无效帧和 §1 所列显示变化。对各场景选择足量、有依据的代表性完整事件，不使用固定片段配额，也不要求四视频每一秒全文标注；一个场景的某个子事件完成不自动代表其余必需转换已覆盖。
- **收口条件**：覆盖矩阵每个场景/变化项都已有处理结论。存在且能可靠核验的选定范围须完成连续保帧、双遍核读、差异解决与完整性检查；缺失、截断或经核查仍不能可靠核验的范围，须保留原帧/来源、已做核查、具体原因和影响，标“待验证”，不列入拟冻结评分范围。不允许仅因尚未处理或较难而把已有可核验场景跳过后宣称收口；也不因素材缺项要求补录、伪造 GT 或无限等待不存在的材料。统一包须同时提交可冻结候选和全部缺口，不宣称缺口通过。
- **触发**：上述收口条件全部满足后，才一次性提交统一审阅版本并触发人工卡点。中间进度或预览材料不触发卡点；拟冻结的扩充及实质修订也在其全部受影响场景处理完成后统一重新提交，旧批准不能覆盖新增或修订范围。
- **材料**：在 `reports/gt-review/<review-id>/` 提供可直接打开的审阅入口，包含源媒体/候选 GT 版本与 SHA-256、会话划分与选片理由、范围与覆盖缺口、按时间排列的原帧及放大区域和文字对照、每个状态的起止帧/PTS、转换前后帧、双遍复核差异与处理依据、未解决问题，以及完整标注和原帧定位方式。摘要不得代替完整可追溯材料，不能只展示成功或容易的页面。
- **选片审阅**：逐片解释“为什么从这里开始、到这里结束”，展示事件前、过程和结束后的原帧；明确热身/评分/结束后上下文的边界及首次出现、加载完成、替换/消失等关键帧。附截断或边界不确定候选清单和原因，以及连续帧数量、时间与像素哈希一致性检查。裁剪和最近邻放大仅供辅助，须可回到完整原帧。
- **停止与批准**：全部场景统一包正式提交时，才在唯一 ExecPlan 记录“等待用户审阅”、覆盖矩阵收口结论、材料路径/版本/哈希、拟冻结范围和批准后下一步，并明确请求审阅。此时暂停后续开发、GT 冻结和被测 OCR/翻译执行；不得以其他独立任务绕过卡点。等待期间仅可响应用户反馈、修订审阅材料并做相关检查。沉默、超时、之前的一般开发授权或流程调整都不等于批准该版 GT。
- **恢复**：只有用户明确批准所提交的具体版本/范围，才记录其原话或可追溯消息依据、日期和对应哈希；重新核对文件与批准版本一致、完整性检查通过后冻结并继续。拒绝或要求修改时修订、复核、重新提交；文字、边界、范围、会话划分或来源证据变化均使受影响材料需重新审阅，旧批准只对旧版本有效。
- **证据边界**：用户审阅批准只表示允许使用该版标注继续，不等同于用户已逐帧核验，也不等同于 OCR 独立验收通过；未解决范围仍不能冻结，M4→M5 门槛不变。审阅材料是证据附件，不另建进度账本。

## 4. 分阶段验收（按真实证据判定）

| 验收项 | 通过条件 |
| --- | --- |
| **离线 GT 完整性** | 本次冻结评分范围 **100% 原帧/原时间/可见状态机会**都有独立核验依据，未知、冲突、漏帧、时间缺口为 0；`acceptance` 若作为独立验收须满足会话隔离 |
| **原始日文 OCR** | 冻结评分集字符准确率 **≥99.5%**、整页正确率 **≥95%**，且原始输出不借助源码文本候选修正/中文映射 |
| **最终日文 OCR** | 冻结范围字符/位置/字段/整页 **100% 正确**，所有目标转换正确；空/非目标画面错误文字为 **0**。使用日文辅助纠正须保留可审计的依据；不用纠正时原始输出也要达到此门槛 |
| **生产中文映射** | 已审计范围中**唯一完整日文消息**和**可确定的固定显示页面**，分别达到 **≥95% 经核对中文映射覆盖**；未知/动态/未解释路径单列，未审计不能凑分母 |
| **中文与端到端** | 中文 GT 中应译机会 **100% 正确**；无提前显示后文、错名/数值/否定、误拼接、过期或非目标译文 |
| **时延** | 完整文字独立出现→**正确结果实际在 UI 呈现 ≤200 ms**；清屏/退出/换源→**旧译文实际消失 ≤200 ms**；短于 200 ms 的完整页面仍计机会，必须在其有效显示期内输出 |
| **真实运行环境** | 四版本及必需场景、整倍/非整倍缩放、真实目标窗口非前台/遮挡捕获等有对应实测；已有四视频的原速回放连续 **≥2 h**，真实投屏另连续 **≥2 h**，无崩溃、死锁、队列/缓存失控或持续异常内存增长 |

**计算细则**：字符准确率 = `max(0, 1 − (替换+删除+插入)/预期字符数)`，在相应行/区域按最小编辑距离计分；不可删除空格、清浊点、大小假名、数字与标点以提高成绩。空预期单独考核误报。整页须当前全部目标文字、字段、位置与状态一致，漏检、多识别、迟到算失败。页面机会指一次完整可见状态到被替换/移除为止；相同文字再次出现算新的机会，菜单光标变化与清屏也须单独验证。**未知 GT 不计为通过，也不可以按零字符消除分母。**

**评分实现契约（M2 冻结，先于被测 OCR）**：

- 逐帧 OCR 按输入源帧关联结果，所有评分原帧（含逐字加载态）逐帧累计编辑错误与预期字符数；另按每次连续可见状态等权报告字符准确率，二者均须满足原始 OCR 门槛，防止静止长页掩盖短状态错误。状态内逐帧错误数和字符数分别除以该状态帧数后再累计；同一文字再次出现为新状态。缺输出按删除、额外输出按插入计，空预期误报另列且不得遗漏。
- 区域按冻结的位置、字段角色和阅读顺序匹配，不根据识别文本挑选最佳区域。坐标同时保存源帧像素的半开矩形和标准游戏画面的字格行列；位置正确以区域、字格占位和字段归属完全一致判定。源帧到标准网格的映射及字格边界在 GT 中冻结，不以 OCR 输出反定位置；像素边框差异另报。
- 帧内容正确性与实时呈现分开评分：逐字加载只要求该帧实际可见内容，不借后帧补全；完整页机会按首次完整帧至替换/移除判定。完整页输出必须在 ≤200 ms 且页面仍有效时实际呈现；输出内容与其来源帧绑定，过期结果不能算命中。所有中间帧仍保留并评分，不因时延预算删除。
- 整页正确率按完整页机会计数，不按停留时长加权；加载、光标、滚动、清屏等转换另列逐机会结果。M2 在同一 ExecPlan 记录最终 JSON 字段、字符编码单位（含浊点组合表示）、区域匹配算法和例子，禁止按 OCR 成绩调整。

**中文覆盖分母**：M5 在建设映射前冻结四版本的来源提交、目标文件/消息范围、消息和固定页面的去重规则、变量模板规则及排除理由。分别报告各版本/必需场景的目标总量、已审计量、未知项和映射覆盖；无法确定目标总量时明确未知。不得通过只审计易译条目或事后缩小范围达到 95%；修改范围必须保留旧版本和差异。已审计范围的通过不能替代未审计范围的验收。

**时延证据**：使用独立帧时间线确认事件起点，另用实际 UI 呈现/消失的观测证据确定终点；主程序自己记录“稳定”时刻、线程计算完成或 UI 提交日志**不能**替代实际呈现。报告 P50/P95/P99、最大值、超时及漏译，最大值不得被平均数掩盖。

**稳定性**：两种 ≥2 h 测试在开始前冻结队列、缓存与诊断文件上限，预热 10 分钟，其后每分钟记录进程/堆、队列、缓存；末 20 分钟样本中位数比首 20 分钟增长不超过 `max(首段的 5%, 16 MiB)`，且没有持续增长趋势。禁止中途重启、人工清缓存或调大上限。重复播放四段录像**只提高运行时长，不增加独立内容覆盖**。

持续增长趋势至少检查预热后各连续、不重叠 20 分钟窗口的中位数：进程内存和堆内存分别判定，连续三个窗口严格增加且第三窗口比第一窗口增长超过 `max(第一窗口的 5%, 16 MiB)` 时判失败；末首窗口门槛仍独立适用。队列/缓存必须始终不越预先冻结的上限，并报告积压是否恢复。保留全部分钟样本，不以整体平均数替代上述检查。

**证据边界**：离线样本不足、会话无法隔离、版本/场景未出现或缺真实窗口设备时，相关项目一律写“待验证”；不强制用户录制新视频，也不能声称“全部通过”。构建成功、合成素材和四录像局部通过都不能取代最终实测。

## 5. UI、诊断与交付

UI 至少提供窗口选择、开始/暂停、自动/手动区域、置顶、缩放、原文/译文切换、文字复制、采集异常提示，并根据对话/战斗/列表/PC/商店切换显示布局。采集、处理、UI 分线程；队列/缓存有界，过期结果须在清屏、换源、调整区域、窗口失效时丢弃。

诊断需关联源帧及 PTS、裁剪/字格/预处理、原始与修正 OCR、候选和状态、匹配/变量/中文来源、实际 UI 时间与各阶段耗时。失败留取相邻连续帧并限制磁盘占用。

最终交付：可构建源码与启动说明、固定来源及许可检查、针对**现有 4 段录像**的确定性测试脚本、已冻结 GT/报告和真实环境报告；无再发行权的录像或游戏素材不随产品分发。报告清楚区分**已验证范围**与**未验证缺口**。
