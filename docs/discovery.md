# 宝可梦初代 VC OCR 翻译设计讨论

本项目将采集软件中的 3DS Virtual Console 日版宝可梦游戏画面转换为便于游玩时阅读的简体中文翻译。Q1–Q32 已确认产品边界与主要技术选择，已形成技术设计、数据契约、验收方案和大模型执行说明。当前等待共同理解的总确认，尚未开始产品实现。

## 仓库现状

- 根目录 `README.md` 描述的目标是 Windows 本地工具，识别 3DS VC 日版《宝可梦 红、绿、蓝、皮卡丘》的投屏画面，并在独立窗口显示当前可见内容的中文翻译。
- 仓库尚无应用实现；`testpic/pic/` 有 16 张 PNG，按文件名分为对白、战斗、背包、商店、PC 和菜单。
- 16 张样本均为 645 × 580 像素的 RGB 图像，只显示游戏内容。样本没有可见的桌面窗口边框；实际投屏输入的尺寸、缩放和边界仍须单独验证。
- `AGENTS.md`、`.agent/EXECPLAN.md`、`.agent/PLANS.md` 和 `spec.md` 当前处于已有的暂存删除状态。本轮不恢复这些文件，也不以其历史内容作为当前约束。

## 已确认的产品边界

- 平台与输出：Windows 本地工具，独立窗口显示简体中文。
- 技术选择：Java 8 与 JavaFX 8，明确不使用 C#。Q32 确认 JNA 直接调用系统 WGC，不维护自有采集 DLL；标准 JNA 与 JavaFX 原生组件允许随包提供。具体实现尚未实测。
- 最终游戏范围：3DS VC 日版《红、绿、蓝、皮卡丘》。四作共享 OCR 核心与公共文本库；先以红版完成闭环，再验证其他版本。
- 公共库：共同内容合并，必要的文本、分页和来源差异保留为库内变体，所有条目共用识别和检索流程。
- 输入前提：设备画面能完整投送到采集软件。本项目从采集软件中的画面开始，不要求了解主机型号和投屏工具，不承担主机侧投屏搭建。
- 采集行为：类似 OBS 的窗口采集，目标窗口被其他窗口遮挡时仍可采集；默认自动定位实际游戏区域，屏蔽采集软件的非游戏内容。处理窗口移动与缩放，自动定位失败时才提供人工框选。
- 输入范围：游戏完整显示、宽高比正确、实际尺寸至少为原生 160 × 144，支持整数和非整数等比放大。
- 窗口状态：最小化时暂停，恢复后自动重新定位；窗口关闭时回到待选窗口状态。
- 首版场景：对白、战斗、背包、商店、PC、菜单；允许分阶段完成，六类均须纳入首版验收。
- 内容边界：仅当前实际可见的文字；不补全被遮挡的文字，也不推测滚动列表中的屏幕外内容。
- 更新方式：默认自动更新，提供暂停和手动重试；文字完整、识别和翻译正确、译文对应当前页面优先于响应速度。
- 防闪规则：新结果确认后整块替换，短暂滚动或失败保留完整旧译文；持续超过 150 ms 标记更新中，最长暂留 1 秒，确认区域无文字持续 150 ms 后清除。各区域独立更新，关联菜单组一起提交，最长暂留计时从首次不一致算起且不被失败重置；时间作为可调初值。
- 展示方式：独立文字面板，提供采集预览与原文查看。保持各区域相对锚点和顺序，区域尺寸适配中文，自动换行，溢出时可展开完整阅读。
- 运行时翻译：识别日文，匹配本地原文或游戏文本模板，再检索预先准备的中文；不在运行时生成新译文。
- 字形识别：恢复原始网格和二值点阵后，以位图完全相等查表，再按字形序列匹配文本库。共用位图的假名归为字形等价项；未命中时先检查定位、采样和字体配置，不把模糊字符猜测作为默认方案。
- 短期证据：允许同一页面相邻帧与紧邻已见片段辅助识别、定位，切换时隔离历史，不显示未见内容。
- 等价输出：多个来源候选对应相同中文和相同变量填充值时可直接输出，无需确认唯一内部来源。
- 基准资源：Narishma-gb 日版反汇编系列和 TomJinW 简体汉化工程；增加 `pret/pokered` 和 `abcboy101/poke-corpus` 作为参考。资源提交版本尚未固定。
- 译文原则：沿用汉化基准译文；只有有原文证据、足以改变关键事实、条件或操作结果的错误才允许修订。措辞、语气、文风和大义不影响理解的差异保留；修订保存原译、修改结果和依据，便于检查和撤回。
- 不确定时：未收录、识别不足或出现多个无法区分的候选时，当前区域显示已识别日文及简短状态，记录待补内容；其他可靠区域正常显示。
- 匹配覆盖：上述状态只作兜底。必须通过自动化建库、识别和匹配改进尽可能提高覆盖，不能把大量未匹配内容交给用户逐条处理作为默认方案。
- 质量目标：自动覆盖率至少 98%、自动输出正确率至少 99.5%，固定标注回放集并按六类场景分别报告失败原因和样本量。稳定有效画面到达采集端后，95% 的译文在 300 ms 内显示，不包含上游投屏延迟。原文兜底不算自动翻译成功，重复视频帧不扩大样本量；计数和计时方案见 [验收方案](validation.md)，具体冻结清单在实施时建立。
- 名字和专名：固定专名使用汉化译名。玩家姓名、劲敌姓名和昵称在库中有明确对应记录时也可翻译；没有可靠对应时保留原文。
- 显示对齐：允许对汉化译文作保持用词与含义的分段、拼接以对应当前可见内容，与语义修订区分。
- 开发和建库：允许联网大模型辅助配对、检查、补译，经核查后固化为本地资源。
- 建库工具：确认使用 Python；最终用户运行打包好的 Java 程序与预构建资源，无需安装或运行 Python。
- 应用运行时不采用云端翻译服务，不需要 API 密钥。资源随包预构建、首版换包更新作为工程默认值，纳入本轮总确认。
- 阶段顺序：先验证严格字形还原与窗口采集兼容性，再扩大全量建库和完整界面。

## 事实证据与待验证风险

公开资源已确认提供日版可读文本、字符映射与字体资产；中文汉化工作表已实际读取，包含按标签组织的中英文和部分日文参考，为自动导入和候选配对提供基础。部分自动匹配参考存在错误，完整对应关系仍须核查；详细证据和未验证事项见 [资源核查](resource-research.md)。不能因为标签或行位置相同就假定句意和可见片段已经正确对应。

Q32 已答“是”。直接系统调用的取舍已记入 [ADR 0006](adr/0006-java8-direct-wgc.md)。严格点阵恢复、JNA 采集链路、日中资源覆盖分别由实施关卡验证；无需用户补充主机型号或投屏工具。
